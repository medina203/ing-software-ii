## Diapositiva 2
REPASO
¿Qué son las pruebas del software?
Proceso para verificar y validar
la funcionalidad de un programa o aplicación ejecutándolo con herramientas manuales o automatizadas, para encontrar defectos y comprobar que cumple los requisitos antes de entregarlo.
VERIFICACIÓN
¿Construimos el producto correctamente?
El software implementa bien cada función especificada.
VALIDACIÓN
¿Construimos el producto correcto?
El software responde a lo que el cliente realmente necesita.
«Las pruebas pueden mostrar la presencia de errores, pero nunca su ausencia.»  
— E. W. Dijkstra

## Diapositiva 4

3

4

## Diapositiva 7
PRUEBAS FUNCIONALES  ·  1 DE 8
Pruebas unitarias
   Unit testing
DEFINICIÓN
Verifican la unidad más pequeña de código que puede aislarse lógicamente (un método, una función o una clase), de forma independiente del resto del sistema. Son las primeras en ejecutarse y las más numerosas.
TÉCNICA / NIVEL
Caja blanca · nivel de componente
¿QUIÉN LA HACE?
El desarrollador, mientras programa
HERRAMIENTAS
JUnit, pytest, NUnit, Jest
CASO DE PRUEBA DOCUMENTADO  ·  CP-UNI-01
Objetivo
Verificar que calcularPromedio() devuelve el promedio ponderado por créditos.
Precondiciones
Clase CalculadoraNotas compilada; sin dependencias externas (BD simulada).
Datos de prueba
notas = [4.0, 3.5, 5.0] · créditos = [3, 2, 4]
Pasos
1. Instanciar CalculadoraNotas.
2. Invocar calcularPromedio(notas, créditos).
3. assertEquals(4.33, resultado, 0.01).
Resultado esperado
Retorna 4.33 → (4.0·3 + 3.5·2 + 5.0·4) / 9 créditos.
Resultado obtenido
Retorna 4.33 en 3 ms.
Estado
✔  PASA

## Diapositiva 8
PRUEBAS FUNCIONALES  ·  2 DE 8
Pruebas de integración
   Integration testing
DEFINICIÓN
Verifican las interfaces y la interacción entre componentes o módulos ya probados de forma unitaria: paso de datos, llamadas entre servicios, acceso a archivos, BD o sistema operativo. Pueden ser incrementales (ascendente o descendente).
TÉCNICA / NIVEL
Caja gris · nivel de integración
¿QUIÉN LA HACE?
Desarrolladores y equipo de pruebas
HERRAMIENTAS
JUnit + Spring Test, Postman, Testcontainers
CASO DE PRUEBA DOCUMENTADO  ·  CP-INT-03
Objetivo
Verificar que Inscripción consulta a Pagos y solo confirma la matrícula si el recibo está pagado.
Precondiciones
Módulos Inscripción y Pagos desplegados en QA; recibo 2026-0981 en estado PAGADO.
Datos de prueba
Estudiante 1120456789 · 5 asignaturas (17 créditos)
Pasos
1. Inscribir las 5 asignaturas desde Inscripción.
2. Inscripción invoca GET /pagos/estado/1120456789.
3. Consultar la tabla inscripciones en BD.
Resultado esperado
Pagos responde PAGADO; se guardan 5 registros con estado CONFIRMADA.
Resultado obtenido
5 registros CONFIRMADA; respuesta de Pagos en 180 ms.
Estado
✔  PASA

## Diapositiva 10
PRUEBAS FUNCIONALES  ·  4 DE 8
Pruebas de sanidad
   Sanity testing
DEFINICIÓN
Prueba rápida, estrecha y enfocada que confirma que un defecto corregido o un cambio puntual funciona de forma razonable, antes de invertir tiempo en pruebas más profundas. Suele ser no guionizada y es un subconjunto de la regresión.
TÉCNICA / NIVEL
Caja negra · enfocada en el cambio
¿QUIÉN LA HACE?
Probador (QA) tras recibir la corrección
HERRAMIENTAS
Manual; lista de verificación corta
CASO DE PRUEBA DOCUMENTADO  ·  CP-SAN-02
Objetivo
Confirmar la corrección del defecto DEF-245 (créditos mal calculados al retirar una asignatura).
Precondiciones
Build 2.3.1 con la corrección de DEF-245 desplegado en QA.
Datos de prueba
Estudiante con 18 créditos inscritos; retira Ética (3 créditos)
Pasos
1. Ir a Mis asignaturas.
2. Retirar Ética.
3. Verificar el total de créditos y el recibo.
Resultado esperado
Total pasa de 18 a 15 créditos y el recibo se recalcula.
Resultado obtenido
Total 15 créditos; recibo recalculado.
Estado
✔  PASA

## Diapositiva 11

Pruebas de humo
   Smoke testing
DEFINICIÓN
Verificación inicial, amplia y superficial de las funciones críticas de una nueva compilación (build) para decidir si es lo bastante estable como para seguir probándola. Si falla, el build se rechaza.
TÉCNICA / NIVEL
Caja negra · punto de control del build
¿QUIÉN LA HACE?
QA o pipeline de CI, en cada despliegue
HERRAMIENTAS
Selenium/Postman en CI (Jenkins)
CASO DE PRUEBA DOCUMENTADO  ·  CP-HUM-01
Objetivo
Decidir si el build 2.4.0 es apto para pruebas detalladas.
Precondiciones
Build 2.4.0 desplegado en QA; datos de prueba base cargados.
Datos de prueba
Usuario de prueba estudiante01 · límite de ejecución: 15 min
Pasos
1. La aplicación carga.
2. Inicio de sesión.
3. Menú principal visible.
4. Consultar notas.
5. Cerrar sesión.
Resultado esperado
Los 5 puntos responden sin error → build ACEPTADO.
Resultado obtenido
El paso 4 devuelve error 500 → build RECHAZADO.
Estado
✘  FALLA — se registra un defecto

## Diapositiva 12
PRUEBAS FUNCIONALES  ·  6 DE 8
Pruebas de interfaz
   Interface testing
DEFINICIÓN
Verifican la comunicación entre dos sistemas de software distintos (API, servicios web, colas de mensajes): autenticación de la conexión, formato de los datos intercambiados, códigos de respuesta y manejo de errores.
TÉCNICA / NIVEL
Caja negra · contrato entre sistemas
¿QUIÉN LA HACE?
Desarrolladores backend y QA
HERRAMIENTAS
Postman, SoapUI, REST Assured
CASO DE PRUEBA DOCUMENTADO  ·  CP-IFZ-04
Objetivo

Precondiciones
Credenciales OAuth del sandbox de la pasarela; servicio disponible.
Datos de prueba
A) token válido · B) token vencido · monto 1.250.000 COP
Pasos
1. POST /api/pagos con el token A.
2. Validar el JSON (idTransaccion, estado).
3. Repetir con el token B.
Resultado esperado
A → HTTP 201 + idTransaccion. B → HTTP 401 con mensaje de error, sin crear el pago.
Resultado obtenido
A → 201 correcto. B → 401 correcto.

✔  PASA

## Diapositiva 13
PRUEBAS FUNCIONALES  ·  7 DE 8
Pruebas de regresión
   Regression testing
DEFINICIÓN
Vuelven a ejecutar pruebas ya superadas después de un cambio (corrección, mejora o nueva función) para garantizar que lo que funcionaba sigue funcionando y que no se introdujeron defectos colaterales.
TÉCNICA / NIVEL
Caja negra/blanca · se automatiza
¿QUIÉN LA HACE?
QA, idealmente de forma automática en CI
HERRAMIENTAS
Selenium, Cypress, JUnit + GitHub Actions
CASO DE PRUEBA DOCUMENTADO  ·  CP-REG-v2.4
Objetivo
Asegurar que el nuevo módulo Homologaciones no afectó funciones existentes.
Precondiciones
Build 2.4.0 aprobado en humo; suite de regresión v2.3 actualizada.
Datos de prueba
Suite de 120 casos: inicio de sesión, inscripción, notas y pagos
Pasos
1. Ejecutar la suite completa en el pipeline.
2. Comparar con la línea base v2.3.
3. Registrar los defectos nuevos.
Resultado esperado
120/120 casos pasan, igual que en v2.3.
Resultado obtenido
118/120 pasan; falla CP-INS-07 (cruce de horario) → DEF-311.
Estado
✘  FALLA — se registra un defecto

Pruebas de aceptación
   Acceptance / UAT, alfa y beta
DEFINICIÓN
Las realiza el cliente o usuario final para decidir si el producto cumple los requisitos y el contrato antes de su entrega. Alfa: en el entorno del desarrollador; beta: en el entorno real del usuario.
TÉCNICA / NIVEL
Caja negra · validación (¿producto correcto?)
¿QUIÉN LA HACE?
Cliente / usuario final con apoyo de QA
HERRAMIENTAS
Cucumber (Gherkin), acta de aceptación
CASO DE PRUEBA DOCUMENTADO  ·  CP-ACE-HU12
Objetivo
HU-12: «Como estudiante quiero que el sistema impida inscribir materias con cruce de horario».
Precondiciones
Registro y Control Académico participa como usuario; pago al día.
Datos de prueba
Ing. Software II (vie 8–10 a. m.) + Redes (vie 9–11 a. m.)
Escenario (Gherkin)
DADO un estudiante con pago al día
CUANDO inscribe ambas asignaturas
ENTONCES ve «Cruce de horario» y no se guarda la segunda
Resultado esperado
Mensaje de cruce y solo 1 asignatura inscrita; el usuario firma el acta.
Resultado obtenido
Comportamiento correcto; acta de aceptación firmada.
Estado
✔  PASA

## Diapositiva 16
PRUEBAS NO FUNCIONALES  ·  1 DE 12
Pruebas de rendimiento
   Performance testing
DEFINICIÓN
Evalúan la velocidad, la capacidad de respuesta y el consumo de recursos del sistema bajo una carga de trabajo esperada o definida. Es la categoría general que agrupa carga, estrés y volumen.
TÉCNICA / NIVEL
Mide tiempos, throughput y recursos
¿QUIÉN LA HACE?
Ingeniero de rendimiento / QA
HERRAMIENTAS
JMeter, k6, Gatling, Lighthouse
CASO DE PRUEBA DOCUMENTADO  ·  CP-REN-01
Objetivo
Verificar el tiempo de respuesta de la consulta de notas en carga normal (RNF-03).
Precondiciones
Entorno de rendimiento con la misma infraestructura que producción.
Datos de prueba
200 usuarios concurrentes · 10 min · 30.000 estudiantes en BD
Pasos
1. Grabar el escenario «Consultar notas» en JMeter.
2. Ejecutar con 200 hilos.
3. Medir el percentil 95 (p95).
Resultado esperado
p95 ≤ 2 s y uso de CPU del servidor < 70 %.
Resultado obtenido
p95 = 1,6 s; CPU al 55 %.
Estado
✔  PASA

Carga esperada máxima, sostenida
¿QUIÉN LA HACE?
Ingeniero de rendimiento / QA
HERRAMIENTAS

Oferta académica 2026-2 cargada; monitoreo de servidores activo.
Datos de prueba
Rampa de 0 a 2.000 usuarios en 10 min; sostener 30 min

1. Configurar la rampa en k6.
2. Ejecutar el escenario «Inscribir asignaturas».
3. Registrar errores y p95.
Resultado esperado
Tasa de error < 1 % y p95 ≤ 3 s durante toda la meseta.
Resultado obtenido
Error = 0,4 %; p95 = 2,7 s.
Estado
✔  PASA

## Diapositiva 18
PRUEBAS NO FUNCIONALES  ·  3 DE 12
Pruebas de estrés
   Stress testing
DEFINICIÓN
Llevan el sistema más allá de su capacidad máxima para encontrar el punto de quiebre y comprobar que falla de forma controlada (sin pérdida de datos) y que se recupera cuando la carga baja.
TÉCNICA / NIVEL
Carga extrema, por encima de la esperada
¿QUIÉN LA HACE?
Ingeniero de rendimiento / QA
HERRAMIENTAS
JMeter, k6, Gatling
CASO DE PRUEBA DOCUMENTADO  ·  CP-EST-01
Objetivo
Encontrar el punto de quiebre del módulo de inscripción y verificar la degradación controlada.
Precondiciones
Prueba de carga CP-CAR-02 superada.
Datos de prueba
Incremento de 2.000 a 10.000 usuarios (+500 cada 2 min)
Pasos
1. Aumentar la carga por escalones.
2. Registrar dónde crecen los errores.
3. Bajar la carga y medir la recuperación.
Resultado esperado
Mensaje «Intente más tarde» (HTTP 503), sin inscripciones corruptas; recuperación ≤ 5 min.
Resultado obtenido
Quiebre en 6.500 usuarios; 503 controlado; se recupera en 2 min.
Estado
✔  PASA

## Diapositiva 23

   Recovery testing
DEFINICIÓN
Fuerzan fallas (caída de servidor, corte de red o de energía) para verificar que el sistema se recupera en el tiempo acordado, sin pérdida ni corrupción de datos. Se mide con RTO (tiempo) y RPO (datos perdidos).
TÉCNICA / NIVEL
Inyección de fallas controladas
¿QUIÉN LA HACE?
QA y equipo de infraestructura
HERRAMIENTAS
Scripts de fallas, Chaos Monkey
CASO DE PRUEBA DOCUMENTADO  ·  CP-REC-01
Objetivo
Verificar la recuperación ante la caída de la BD en medio de un pago.
Precondiciones
Réplica de BD configurada; transacción de pago en curso.
Datos de prueba
Pago de 1.250.000 COP · RTO objetivo 5 min · RPO objetivo 0
Pasos
1. Iniciar el pago.
2. Apagar el contenedor de BD a mitad de la transacción.
3. Medir la conmutación a la réplica y revisar el pago.
Resultado esperado
Rollback sin doble cobro; servicio restablecido en ≤ 5 min; 0 datos perdidos.
Resultado obtenido
Rollback correcto; servicio restablecido en 3 min.
Estado
✔  PASA

## Diapositiva 24
PRUEBAS NO FUNCIONALES  ·  9 DE 12
Pruebas de confiabilidad
   Reliability testing
DEFINICIÓN
Garantizan que el software realiza sus funciones de forma consistente, sin fallar, durante un período determinado y en condiciones específicas. Se miden con indicadores como MTBF y disponibilidad.
TÉCNICA / NIVEL
Ejecución prolongada (soak / endurance)
¿QUIÉN LA HACE?
QA / ingeniero de rendimiento
HERRAMIENTAS
JMeter o k6 de larga duración, Grafana
CASO DE PRUEBA DOCUMENTADO  ·  CP-CON-01
Objetivo
Verificar la operación continua durante la semana de matrícula.
Precondiciones
Monitoreo de memoria, CPU y errores activo.
Datos de prueba
Uso típico: 300 usuarios constantes durante 72 h
Pasos

## Diapositiva 28
PARA NO CONFUNDIRLAS
Pares de pruebas que suelen confundirse
Par
Diferencia clave
Pregunta que responde
Humo vs. sanidad
Humo: amplia y superficial, sobre el build completo. Sanidad: estrecha y enfocada en un cambio.
¿Arranca? / ¿Quedó bien lo corregido?
Integración vs. interfaz
Integración: módulos internos del mismo sistema. Interfaz: frontera con otro sistema.
¿Se entienden mis módulos? / ¿Me entiendo con el otro sistema?
Carga vs. estrés vs. volumen
Carga: usuarios esperados. Estrés: más allá del límite. Volumen: muchos datos.
¿Aguanta? / ¿Cómo se rompe? / ¿Y con millones de registros?
Rendimiento vs. confiabilidad
Rendimiento: rapidez en un momento dado. Confiabilidad: estabilidad a lo largo del tiempo.
¿Qué tan rápido? / ¿Por cuánto tiempo sin fallar?
Sistema vs. aceptación
Sistema: la ejecuta QA contra requisitos. Aceptación: la ejecuta el usuario para decidir si recibe.
¿Cumple lo especificado? / ¿Me sirve?

## Diapositiva 30
Ideas clave
1
Cada tipo de prueba busca una clase distinta de defectos: ninguno reemplaza a los demás.
2
Las funcionales responden QUÉ hace el sistema; las no funcionales, CÓMO lo hace.

Un caso de prueba bien documentado es reproducible, medible y trazable a un requisito.
